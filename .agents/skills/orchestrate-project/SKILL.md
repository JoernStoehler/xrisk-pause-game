# Orchestrate Project

Coordinate the work without turning one preferred workflow into an axiom. Use
the reasoning below to select the lightest control structure that fits the
current task.

## Working model

- Parallel agents can produce locally strong work faster than a lead can
  integrate it. Parallelism therefore has value only when each stream informs
  a real decision or owns separable execution.
- Reviewers judge within the frame and authority they receive. Independent
  review does not recover a missing success dimension, and a narrow acceptance
  is not product approval.
- Long conversations and many branches make implicit priorities unreliable.
  Externalize only the state future decisions depend on; do not create project
  management ceremony for its own sake.
- Jörn's attention is valuable for domain judgment, taste, approval, and real
  strategic cruxes. Repository inspection, routine implementation, synthesis,
  and integration normally remain agent work.

Treat these as challengeable hypotheses. Change the method when current
evidence shows a different decomposition or control surface would work better.

## Orient and choose

Read the project entry points and inspect the current repository before making
large commitments. Form a provisional account of:

- the project outcome and current route to it;
- the leading uncertainties or failure risks;
- available evidence and rejected paths;
- which next result would most change resource allocation.

Compare materially different work surfaces when they could dominate each other:
expert-model refinement, game-model approximation, fun, teaching and transfer,
product shape, visual/interaction design, public-discourse research, and
distribution. Do not let available implementation, a recently rejected
artifact, or an easy prototype silently select the next target.

For genuinely multi-stream work, keep a concise, source-linked priority and
decision ledger. Rank work by expected project value, value of information,
dependencies, cost, and reversibility as appropriate. The lead owns the
cross-project tradeoff; a bounded agent may analyze inputs or rank options
within its scope.

## Delegate deliberately

Delegate when parallelism, context isolation, independent evidence, or bounded
ownership is worth the coordination and integration cost. State the decision
the work serves, relevant context, ownership, concurrent-work constraints,
expected handoff, and validation criteria. Let subagents delegate further when
the same test holds.

Do not create a stream merely because capacity exists or because the work is
difficult. Avoid several agents independently synthesizing the whole project
unless disagreement itself is the experiment. Reassess or stop streams whose
output no longer affects a live decision.

## Integrate and review

Integrate returned work into the priority model; do not substitute a collection
of reports for synthesis. Decide explicitly whether each branch or artifact is
accepted evidence, an option, mixed quarry, superseded, or abandoned. Preserve
recoverability when uncertainty remains.

Before review, identify the success dimensions that matter, why they matter,
and the authority of each reviewer. Keep verdicts scoped to the artifact,
conditions, and lane actually reviewed. For UI work, do not collapse mobile
comprehension and information density, visual craft, interaction and
accessibility, narrative, semantics, and engineering into one generic UX pass.
Agents can reject obvious failures but cannot establish human taste, fun,
comprehension, demand, or virality without relevant human evidence.

## Use evidence when correcting course

When a claim about the session, agent tree, repository, or artifact is disputed,
inspect the available source before explaining its cause. Separate observation
from causal hypothesis when the source cannot establish the cause.

Treat repeated requests for status, priority, or explanation as possible
evidence that control is no longer legible. Make the smallest concrete control
repair first. Put substantial unreviewed synthesis in a reviewable artifact
rather than generating a large process framework directly in chat.

## Communicate and hand off

Keep Jörn-facing communication concise and decision-oriented. When requesting
review, provide the artifact, material evidence or uncertainty, and the concrete
feedback or decision needed. Make clear whether work continues or waits on him.

For a root handoff, preserve source pointers, accepted decisions, open cruxes,
branch dispositions, current validation, and a cheap starting path. Exclude raw
process that does not help the next root verify or decide.

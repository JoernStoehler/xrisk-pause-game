# Coordinate Product Agents

Use this reference before distributing substantial product preparation,
production, or review work among agents.

The integration owner retains the cross-product player path, dependency order,
accepted domain and product boundaries, project-level priority, and merge
decision. Delegate bounded work whose output can be evaluated without adopting
the worker's hidden model of the product.

Parallel preparation is useful when tasks answer distinct questions or own
separate surfaces: source or claim checks, interaction alternatives, copy,
implementation, accessibility, visual critique, semantic review, or test
instrumentation. Avoid parallel full-product implementations while the shared
player promise, game semantics, and interface ownership are unstable; they tend
to duplicate foundations and make local concepts expensive to compare.

Assign preparation workers a named downstream decision, not “gather everything
relevant.” Assign production workers a player state, bounded artifact, source
route, surrounding interface, claim boundary, and owned editing surface. Tell
every worker that other agents may be changing the repository and that it must
not revert their work.

Before scaling an unfamiliar workflow, produce one representative product slice
and review whether it is useful as a new starting point. If it fails, change the
input, decomposition, prompt, ownership, or artifact medium before launching
more workers.

Separate reviews when failure modes differ materially. Domain/semantic fidelity,
player comprehension, interaction and accessibility, visual craft, narrative,
engineering, and product/use-context fit can crowd one another out. These are
possible lanes, not a mandatory checklist: assign only reviews that can change
the named gate. Combine them only when one reviewer can genuinely perform
distinct passes on the relevant evidence. Human evidence remains necessary
where the review route says so.
